# 用户账号、邮箱验证与参与限制方案

## 1. 文档状态

- 状态：草案
- 目标版本：待定
- 主要读者：Questra 维护者、后端与前端开发者
- 当前结论：方案可在现有单进程 Express、React 和 SQLite 架构上增量实现，无需替换管理员认证或改变已有匿名问卷

## 2. 背景与目标

Questra 当前只有单一管理员账号体系。公开问卷的读取和提交接口不要求身份认证，`responses` 也不保存提交者，因此只能依靠按 IP 的进程内限流降低恶意提交，无法可靠识别填写者、限制同一用户的提交次数或建立用户自己的参与记录。

本方案增加一套面向普通用户的“账号密码 + 邮箱验证”身份体系，并把用户身份接入问卷访问与提交策略。设计必须能够继续服务后续的报名、投票、考试或扩展插件等资源，而不是把认证逻辑固定在单一问卷页面内。

完成后应具备以下能力：

1. 用户可以注册、验证邮箱、登录、注销、找回密码和管理自己的基本资料。
2. 管理员可以决定问卷保持匿名、要求登录或要求已验证邮箱。
3. 问卷可以限制每个用户的填写次数、总回收数量和提交间隔。
4. 答卷可以在需要时关联提交者，同时允许旧答卷和匿名答卷继续存在。
5. 身份认证和参与限制可以被其他资源或扩展复用。

## 3. 非目标

首个版本不包含以下能力：

- 第三方 OAuth、短信验证码、企业单点登录或无密码登录。
- 多租户、组织、用户组、复杂角色权限或普通用户管理后台权限。
- 多节点共享 SQLite、跨节点会话和分布式限流。
- 邮件营销、群发通知和完整的异步任务平台。
- 使用 IP、浏览器指纹或 Cookie 作为可靠的唯一身份。

这些能力若以后需要，应在普通用户身份和通用访问策略稳定后独立设计。

## 4. 当前实现与影响地图

### 4.1 当前边界

- `src/app.js` 装配管理员登录、公开路由、限流器和 SPA/EJS 回退。
- `src/admin-account.js` 使用 Node.js `scrypt` 保存唯一管理员密码。
- `src/admin-session.js` 和 `src/middleware/admin-auth.js` 管理管理员会话及兼容 Admin Token。
- `src/routes/public.js` 提供公开问卷读取和答卷提交，当前不识别填写者。
- `src/services/survey-service.js` 负责问卷状态、答案校验、判分和答卷事务。
- `migrations/001_initial.sql` 中的 `responses` 只保存问卷、时间和成绩。
- `client/src/pages/Survey.jsx` 和 `SurveyForm.jsx` 提供公开填写流程。
- `client/src/App.jsx` 目前只维护管理员访问状态。
- `views/` 在缺少前端构建产物时提供兼容页面，也需要保留可理解的认证提示和基本提交能力。

### 4.2 预计影响

| 边界 | 需要调整 | 保持不变 |
| --- | --- | --- |
| 管理员认证 | 设置页增加普通用户与邮件配置入口 | `admin_accounts`、Admin Token 和 `/api/admin/*` 权限不与普通用户合并 |
| 普通用户认证 | 新增账户、会话、验证和重置流程 | 普通用户登录不会获得管理权限 |
| 问卷 | 新增访问模式、次数和总量限制 | 旧问卷默认匿名，原公开 URL 不变 |
| 答卷 | 可关联用户并显示身份信息 | 旧答卷和匿名答卷允许没有 `user_id` |
| API | 新增用户认证接口和公开访问状态 | 管理接口继续使用现有管理员鉴权 |
| 扩展钩子 | 可提供受控的参与者上下文 | 不把密码、会话 Token 或验证 Token 传入钩子 |
| 部署 | 增加邮件服务和站点外部地址配置 | 未启用用户注册时不要求邮件服务 |

## 5. 核心设计决定

### 5.1 管理员和普通用户完全分离

普通用户使用独立的 `users` 和 `user_sessions`。不得复用 `admin_accounts`，也不得让普通用户 Cookie 被管理员鉴权中间件接受。这样可以避免权限边界模糊，并保持 Admin Token 的兼容行为。

### 5.2 身份与访问策略分层

用户服务只回答“当前请求是谁、邮箱是否验证、账户是否可用”。访问策略服务回答“此身份是否能查看或提交某项资源”。问卷服务负责题目、答案和判分，不自行实现登录流程。

建议的通用调用形式：

```js
accessPolicy.authorize({
  resourceType: 'survey',
  resourceId: survey.id,
  action: 'submit',
  subject: req.userAuth?.user || null
});
```

### 5.3 向后兼容匿名问卷

所有已有问卷迁移后默认采用 `anonymous`。旧答卷的 `user_id` 为 `NULL`。只有管理员显式改变问卷访问策略后，公开页面才要求用户登录或验证邮箱。

### 5.4 服务端事务是限制的最终依据

页面加载时显示的剩余次数仅用于用户体验。提交时必须在数据库事务内重新检查问卷状态、用户资格、次数、总量和冷却时间，并在同一事务内写入答卷和计数，防止并发请求绕过限制。

### 5.5 邮件能力可配置、可禁用

没有配置邮件服务时，现有站点和匿名问卷仍可使用，但不得启用需要邮箱验证的访问策略。邮件发送通过服务接口封装，首个实现可采用 SMTP，后续可以增加其他适配器。

## 6. 数据模型

已有迁移不可修改。实施时新增下一个有序迁移文件；以下表名和字段在编码前应结合迁移序号最终确认。

### 6.1 `users`

| 字段 | 建议类型 | 说明 |
| --- | --- | --- |
| `id` | `TEXT PRIMARY KEY` | 随机 UUID，不暴露自增规模 |
| `email` | `TEXT NOT NULL` | 用户用于展示和通知的邮箱 |
| `email_normalized` | `TEXT NOT NULL UNIQUE` | 去除首尾空格并转小写后的唯一值 |
| `display_name` | `TEXT NOT NULL` | 展示名称，不作为登录凭据 |
| `password_hash` | `TEXT NOT NULL` | scrypt 哈希 |
| `password_salt` | `TEXT NOT NULL` | 每个用户独立随机盐 |
| `status` | `TEXT NOT NULL` | `pending`、`active`、`locked` 或 `disabled` |
| `email_verified_at` | `TEXT` | 未验证时为 `NULL` |
| `failed_login_count` | `INTEGER NOT NULL DEFAULT 0` | 连续失败次数 |
| `locked_until` | `TEXT` | 临时锁定截止时间 |
| `created_at` | `TEXT NOT NULL` | 创建时间 |
| `updated_at` | `TEXT NOT NULL` | 更新时间 |

### 6.2 `user_sessions`

| 字段 | 建议类型 | 说明 |
| --- | --- | --- |
| `token_hash` | `TEXT PRIMARY KEY` | 原始 Token 的 SHA-256，不保存原文 |
| `user_id` | `TEXT NOT NULL` | 引用 `users.id` |
| `expires_at` | `TEXT NOT NULL` | 会话过期时间 |
| `last_seen_at` | `TEXT` | 可按较低频率更新，避免每请求写库 |
| `revoked_at` | `TEXT` | 主动注销或全端退出时间 |
| `created_at` | `TEXT NOT NULL` | 创建时间 |

IP 和 User-Agent 只有在明确需要安全审计且确定保留周期后才保存；不得默认无限期收集。

### 6.3 `user_auth_tokens`

| 字段 | 建议类型 | 说明 |
| --- | --- | --- |
| `token_hash` | `TEXT PRIMARY KEY` | 一次性随机 Token 的哈希 |
| `user_id` | `TEXT NOT NULL` | 所属用户 |
| `purpose` | `TEXT NOT NULL` | `verify_email` 或 `reset_password` |
| `expires_at` | `TEXT NOT NULL` | 验证邮件建议 24 小时，重置密码建议 1 小时 |
| `consumed_at` | `TEXT` | 使用后立即写入，阻止重放 |
| `created_at` | `TEXT NOT NULL` | 创建时间 |

同一用户重新发送某种 Token 时，使此前未使用的同类型 Token 失效。

### 6.4 `survey_access_policies`

| 字段 | 建议类型 | 说明 |
| --- | --- | --- |
| `survey_id` | `TEXT PRIMARY KEY` | 与问卷一对一，删除问卷时级联删除 |
| `access_mode` | `TEXT NOT NULL` | `anonymous`、`account`、`verified_email` |
| `require_login_to_view` | `INTEGER NOT NULL DEFAULT 0` | 是否在返回题目前要求登录 |
| `max_submissions_per_user` | `INTEGER` | `NULL` 表示不限；仅对可靠用户身份生效 |
| `max_submissions_total` | `INTEGER` | `NULL` 表示不限 |
| `cooldown_seconds` | `INTEGER` | 同一用户两次提交的最短间隔 |
| `starts_at` | `TEXT` | 可选开放时间，与现有截止时间共同判断 |
| `updated_at` | `TEXT NOT NULL` | 最后更新时间 |

第一版不建议对匿名填写提供“每人次数”承诺。匿名模式可以继续使用 IP 限流，但界面必须明确它只是防滥用措施。

### 6.5 答卷关联

为 `responses` 新增可空的 `user_id`，并创建 `(survey_id, user_id, submitted_at)` 索引。是否保存邮箱快照应在隐私策略确定后决定；默认优先通过当前用户记录展示，账户删除后将关联置空或匿名化，而不是删除历史答卷。

如后续资源需要相同计数能力，再引入通用 `participation_counters`。首个版本可以直接基于 `responses` 在事务中计数，以减少重复状态；只有性能数据证明查询成为瓶颈，或第二种资源开始复用时，再增加计数表。

## 7. API 契约草案

### 7.1 用户认证接口

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `POST` | `/api/user/auth/register` | 注册账户并发送验证邮件 |
| `POST` | `/api/user/auth/verify` | 消费邮箱验证 Token |
| `POST` | `/api/user/auth/resend-verification` | 重新发送验证邮件 |
| `POST` | `/api/user/auth/login` | 邮箱和密码登录 |
| `POST` | `/api/user/auth/logout` | 注销当前普通用户会话 |
| `GET` | `/api/user/auth/me` | 获取当前普通用户及验证状态 |
| `POST` | `/api/user/auth/forgot-password` | 请求密码重置邮件 |
| `POST` | `/api/user/auth/reset-password` | 消费 Token 并设置新密码 |
| `PUT` | `/api/user/profile` | 更新展示名称等基本资料 |
| `PUT` | `/api/user/password` | 验证当前密码后修改密码 |

注册、登录、重新发送邮件和找回密码分别限流。涉及账户是否存在的响应使用统一措辞，避免邮箱枚举。

### 7.2 普通用户会话

Cookie 建议名称为 `questra_user_session`，设置 `HttpOnly`、`SameSite=Lax`、`Path=/`，HTTPS 下增加 `Secure`。数据库只保存哈希。管理员的 `questra_session` 保持不变，两者不能互相授权。

所有使用 Cookie 的写操作必须检查同源 `Origin`/`Sec-Fetch-Site`，或引入 CSRF Token。具体方式在实现身份基础阶段确定并记录测试。

### 7.3 公开问卷读取

匿名问卷继续返回当前结构。需要身份的问卷增加受控访问状态，例如：

```json
{
  "accessPolicy": {
    "mode": "verified_email",
    "requiresLogin": true,
    "requiresVerifiedEmail": true,
    "maxSubmissionsPerUser": 1,
    "remainingSubmissions": 1
  },
  "viewer": {
    "authenticated": false,
    "emailVerified": false
  }
}
```

当 `require_login_to_view` 为真且用户不符合要求时，接口只返回问卷标题、站点展示信息和访问要求，不返回题目。

### 7.4 提交接口

提交路径保持 `POST /api/surveys/:id/responses`。服务端从普通用户 Cookie 获取身份，不接受客户端传入 `userId` 或邮箱作为身份依据。

建议错误语义：

| 状态码 | 条件 |
| --- | --- |
| `401` | 问卷要求登录，但没有有效用户会话 |
| `403` | 邮箱未验证、账户禁用或不符合访问条件 |
| `409` | 达到用户次数、总回收量或冷却限制 |
| `410` | 问卷关闭、尚未开放或已经过期 |
| `429` | 登录、邮件或提交请求频率过高 |

## 8. 服务与模块边界

建议新增或拆分以下模块，最终命名沿用实际仓库风格：

```text
src/user-account.js                 普通用户校验、密码哈希和资料更新
src/user-session.js                 普通用户会话创建、查询、撤销和清理
src/middleware/user-auth.js         从 Cookie 恢复可选或必需用户身份
src/services/auth-token-service.js  邮箱验证和密码重置 Token
src/services/email-service.js       邮件发送接口和配置校验
src/services/access-policy.js       资源访问与参与限制判断
src/routes/user-auth.js             普通用户认证 API
```

密码哈希的底层实现可以抽取为内部共享工具供管理员和普通用户调用，但两个账户域的业务规则、会话 Cookie 和路由必须保持分离。

`survey-service.saveResponse` 应接收由服务端确定的参与者上下文，并在事务内完成最终授权和写入。不要让路由先计数、服务再保存形成竞态窗口。

## 9. 邮件服务与配置

### 9.1 配置边界

建议增加以下概念：

- 对外站点基址，例如 `publicUrl`，用于生成不能依赖请求 Host 的验证链接。
- 邮件发送开关、传输方式、发件人和 SMTP 连接参数。
- 注册开关、用户会话有效期和邮件 Token 有效期。

敏感参数优先来自环境变量，不能通过管理 API 原样返回。后台只显示“已配置/未配置”和非敏感摘要。

### 9.2 发送行为

首个版本可使用一个维护活跃、支持 Node.js 22 的 SMTP 依赖。引入前检查包体、许可证、传递依赖和发布包影响。邮件接口至少支持验证邮箱和重置密码两种模板。

发送失败时不得创建虚假的成功状态。注册记录可以保留为 `pending` 并允许重发；接口返回可理解错误，但日志不得输出 Token 和完整邮件正文。

如同步 SMTP 延迟影响请求，后续新增持久化邮件任务表和后台发送器，不能使用只存在于内存的队列承诺可靠送达。

## 10. 前端交互

### 10.1 新增页面

```text
/user/login
/user/register
/user/verify
/user/forgot-password
/user/reset-password
/user/profile
```

登录和注册完成后支持安全的站内 `returnTo`，默认回到来源问卷。只能接受以 `/` 开头且不以 `//` 开头的站内路径，防止开放重定向。

### 10.2 问卷页面状态

公开问卷页至少覆盖：

- 匿名且可填写。
- 需要登录，提供登录和注册链接。
- 已登录但邮箱未验证，提供重新发送入口。
- 已达到填写次数或处于冷却时间。
- 总回收量已满。
- 满足条件，可以填写并显示剩余次数。
- 会话在填写过程中失效，保留本地输入并引导重新登录。

### 10.3 管理后台

在设置中增加“用户与认证”，显示注册开关、邮件配置状态、会话策略和隐私设置。问卷编辑器增加“访问与限制”区域。答卷页面和导出功能按管理员选择展示受控的提交者信息，默认避免导出完整邮箱。

### 10.4 EJS 回退

生产前端缺失时不能绕过访问策略。EJS 回退页面至少要能展示登录/验证要求和拒绝原因；若第一阶段暂不提供完整 EJS 用户表单，应明确引导到对应 HTML 路由，而不是返回题目或允许匿名提交。

## 11. 安全与隐私要求

- 密码使用带独立随机盐的 scrypt；比较哈希时使用恒定时间比较。
- 原始会话 Token、验证 Token 和重置 Token只发送给用户，数据库仅保存哈希。
- 登录失败响应不区分邮箱不存在、密码错误或未验证。
- 注册、登录、验证、重发和重置采用独立限流，并组合 IP 与规范化邮箱键。
- 连续失败触发短期账户锁定；成功登录后清零失败计数。
- 密码修改、密码重置、邮箱修改和账户禁用后撤销所有已有用户会话。
- 邮箱修改需要重新验证新邮箱，旧邮箱在完成验证前保持账户可恢复。
- HTTPS 是生产环境启用账户系统的前置条件。
- 请求日志、钩子和错误信息不得包含密码、认证 Token 或完整邮箱。
- 明确账户注销、答卷保留、邮箱匿名化和备份中的数据保留规则。
- 管理端展示和导出个人信息需要最小化，默认隐藏邮箱的一部分。

## 12. 分阶段实施计划

所有步骤初始均为未开始。实施时逐项更新状态和实际偏差。

### 阶段 A：确认产品与部署决定

- [ ] 确定是否允许站点管理员关闭注册，以及关闭后已有用户是否仍可登录。
- [ ] 确定第一版邮件传输只支持 SMTP，还是同时提供自定义发送钩子。
- [ ] 确定账户注销后答卷保留、匿名化和导出规则。
- [ ] 确定会话、验证邮件和密码重置的默认有效期。
- [ ] 确定“每用户次数”只适用于登录用户，不对匿名用户做唯一身份承诺。

完成条件：待决事项形成明确决定，配置和 API 不再存在互相冲突的含义。

### 阶段 B：身份数据与后端基础

- [ ] 新增有序迁移，创建普通用户、用户会话和一次性 Token 表及索引。
- [ ] 抽取可复用的密码哈希底层工具，同时保持管理员账户行为不变。
- [ ] 实现普通用户账户、会话和一次性 Token 服务。
- [ ] 实现可选身份与强制身份两种用户认证中间件。
- [ ] 实现注册、验证、登录、注销、重发验证和密码重置 API。
- [ ] 增加同源写请求保护、分用途限流、临时锁定和会话撤销。

完成条件：普通用户可以完整完成注册到登录流程；管理员会话和 Admin Token 的现有测试继续通过。

### 阶段 C：邮件服务

- [ ] 扩展配置加载和示例配置，支持外部站点 URL 与邮件参数。
- [ ] 实现邮件服务接口、SMTP 适配器和两种文本/HTML 模板。
- [ ] 处理未配置、连接失败、发送失败和重发场景。
- [ ] 在后台只暴露非敏感配置状态，不返回密码。

完成条件：测试传输器能够验证邮件内容和链接；真实 SMTP 验证作为部署者外部步骤明确记录。

### 阶段 D：问卷访问策略与答卷绑定

## 13. 验证计划

实施过程中按影响范围集中验证，不在每个小步骤后重复完整流程。

### 13.1 数据库

- 空数据库能依次执行所有迁移。
- 具有旧问卷和旧答卷的数据库可升级，数据不丢失，旧答卷的用户关联为空。
- 重复执行迁移不会重复建表或破坏数据。
- 外键删除、会话清理和账户匿名化符合已确认策略。

### 13.2 认证

- 注册输入规范化、重复邮箱、弱密码和禁用注册。
- 验证 Token 的正常使用、过期、重放、重发失效和错误用途。
- 登录成功、错误密码、临时锁定、禁用账户和未验证账户策略。
- 注销、全端撤销、密码修改和密码重置后旧会话失效。
- 管理员 Cookie、普通用户 Cookie 和 Admin Token 互不越权。
- CSRF/Origin 和开放重定向防护。

### 13.3 问卷访问与提交

- 旧匿名问卷读取、提交、判分和钩子行为保持兼容。
- `account` 与 `verified_email` 的允许和拒绝路径。
- 每用户次数、总量、冷却、开放时间、截止时间和关闭状态的组合。
- 两个并发请求不能同时越过剩余一次的限制。
- 用户禁用或会话过期后不能继续提交。
- 考试标准答案仍不通过公开接口泄露。

### 13.4 前端

- 用户认证各页面的成功、错误、加载和失效状态。
- 登录后安全返回原问卷，非法外部 `returnTo` 被拒绝。
- 表单填写中会话失效后内容不会无提示丢失。
- 桌面、窄屏、浅色和深色主题下无溢出或遮挡。
- 无生产前端构建产物时，EJS 回退不会绕过认证和次数限制。

### 13.5 发布边界

- 依赖变化正确更新 `pnpm-lock.yaml`，npm 仍可完成源码安装和构建。
- 新增迁移、视图和前端产物进入发布包，密钥、邮件凭据、数据库和 Token 不进入包。
- 只有本功能跨越的共享边界均稳定后，才运行完整 `check` 和发布包检查。

## 14. 迁移、回退与兼容

- 新迁移只增加表、可空字段和索引，不改写 `001` 至 `005`。
- 已有问卷未配置策略时按匿名处理，避免升级后突然要求登录。
- 已有答卷的 `user_id` 保持 `NULL`，不尝试根据答案或 IP 追溯用户。
- 关闭用户注册或邮件服务不删除账户和答卷；已启用的强制邮箱策略需要在后台显示配置冲突并阻止错误发布。
- 应用版本回退不能自动撤销数据库迁移。发布说明应要求升级前备份；旧版本若无法识别新增结构，应至少忽略附加表和可空字段。
- 若邮件发送服务故障，匿名问卷继续工作，已登录用户可以使用不要求新验证邮件的功能。

## 15. 可观测性

建议记录不含个人敏感信息的安全事件：注册请求、验证成功、登录失败类别、账户锁定、重置密码、策略拒绝和次数上限拒绝。日志使用用户 ID 或脱敏标识，禁止记录完整邮箱和任何原始 Token。

可增加以下聚合指标，但不引入新的监控依赖作为首版前提：

- 注册和验证成功数量。
- 登录失败与锁定数量。
- 邮件发送失败数量。
- 按原因分类的问卷访问拒绝数量。
- 达到用户次数或总量上限的数量。

## 16. 最终验收条件

只有同时满足以下条件，方案才可标记为已完成：

- 普通用户与管理员身份域严格分离且不存在权限提升路径。
- 用户可以完成注册、邮箱验证、登录、注销和密码重置闭环。
- 匿名、登录和已验证邮箱三种问卷模式行为正确。
- 服务端原子执行填写次数、总量和冷却限制。
- 旧数据库、旧问卷、旧答卷及 Admin Token 行为保持兼容。
- 邮件和认证配置不会泄露秘密，HTTPS 与外部 URL 前置条件有明确说明。
- 相关后端、前端、迁移和发布边界验证通过。
- `usage.md`、`installation.md`、`api.md` 和 `development.md` 已按读者任务归类稳定说明，没有用方案书替代正式文档。

## 17. 待确认事项

开始阶段 B 之前需要完成以下产品决定：

1. 第一版是否开放所有访客自行注册，还是同时支持管理员关闭注册。
2. 邮件发送只支持 SMTP，还是允许配置自定义发送钩子。
3. 未验证邮箱是否允许登录但只能看到验证提示，或直接拒绝创建会话。推荐允许登录并限制受保护操作，便于重发验证邮件。
4. 用户注销账户时，历史答卷是匿名保留、连同答卷删除，还是由问卷管理员选择。推荐匿名保留，并在用户注销前明确告知。
5. 答卷页面和导出默认显示展示名称、脱敏邮箱还是不显示身份。推荐页面显示展示名称和脱敏邮箱，默认导出不包含完整邮箱。
